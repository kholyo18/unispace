# Original post publication

Local implementation; automated tests and device validation deferred by the user.

The main _newPost composer now calls reserveOwnPost with a generated postId before its existing uploads, then publishOwnPost with exactly the seven content fields used by editOwnPost. It no longer supplies author identity, privacy flags, timestamps, counters or status writes. The reservation keeps the existing uploading state and media paths, permitting Storage policies to check a server-established post owner. Readers must exclude uploading documents, which now contain only authorId/status/createdAt.

Both endpoints verify a non-revoked bearer token, UID, auth_time and tenant absence, and transactionally check session cutoff, account availability, stored ownership and the deletion receipt. postPublicationReceipts is server-only. Reservation cannot overwrite another post or reuse a deleted ID. Publication requires that reservation, validates content using the existing editor schema, and checks all media against actual token-bearing bucket objects under this post's images/videos prefix. Author name/photo use server profile data with Firebase Auth fallback; privacy comes from the current transactional user snapshot. Initial counts and timestamps are server-generated. The createdAt timestamp at publication prevents a long upload from backdating a new published post in feeds.

A canonical content hash in the receipt makes repeated publication with the same post ID/payload return an acknowledgement without rewriting an edited/moderated post or resetting engagement. Different payloads on a published ID fail. Deleted posts cannot be resurrected. This is request-level retry handling; manually reopening the composer generates another ID, so an uncertain response instructs the user to refresh before retrying. There is no offline draft resumption yet.

The client no longer marks a post failed after an unrelated list refresh error. Acknowledged publication followed by refresh failure is reported separately. Upload errors leave an uploading reservation; abandoned reservations and orphan media still need bounded server cleanup. Storage metadata checks are outside the database transaction and do not establish immutable objects, uploader ownership, MIME safety or malware scanning. Storage policy remains outstanding.

Follower notification documents are now created in the publication transaction for up to 40 eligible followers; see NEW_POST_NOTIFICATIONS.md. Device push delivery and preference synchronization remain separate work. Repost publication and moderation writers remain separate work. Existing raw readers, rules and author-metadata synchronization still require review. Neither these code changes nor the partial root rules have been deployed. Deploy callables and a complete reviewed policy before the client; do not deploy the partial rules alone.
