# Server-owned comment creation

Local implementation; tests and device validation are deferred at user request.

createComment accepts only postId, commentId, text (up to 10000 characters), replyToId and optional media URL/type. Authenticated identity, display name (never email fallback), photo and timestamp come from the server. Authorized content preflight and transaction checks enforce current primary post availability, private-account access, whoCanComment (everyone/followers/mutual/none), accepted followers, both block directions, account state and revocation cutoff. Reply ancestors must exist and be available/unblocked, including moderator-hidden IDs. Repost-original and Firebase Auth state are preflight snapshots; primary Firestore state is rechecked in the transaction.

Comment tree, root count, authored_comments mirror and reply/post-owner notification documents commit together. Repeating the same ID and payload does not insert twice or notify twice; reusing IDs with different contents is rejected. Client manual resubmission currently allocates a new ID, so a lost response requires refreshing before another submission. Nested storage and Firestore document-size limits remain. Push delivery remains asynchronous via the existing notification trigger.

Media uploads now use community_posts/{postId}/comments/{uid}/{commentId}/media.{extension}. The server accepts only the configured Firebase Storage bucket, this exact path, an existing object and its download token; it never fetches arbitrary URLs. COMMENT_MEDIA_BUCKET defaults to the bucket already in lib/firebase_options.dart and must match deployment. Verify storage rules permit only the owner to write these paths. Existing media remains readable. This is URL/path validation, not malware/MIME scanning or proof of upload ownership in the absence of correct storage rules. Failed submissions can leave orphan uploads; cleanup is pending.

The shared _postComment helper used by main/reply composers calls the endpoint and no longer writes the post tree, author mirror or sends client-side creation notifications. The main composer permission hint is server-derived; final enforcement is transactional. The partial local Firestore rules were not replaced/deployed; direct legacy writes elsewhere and comment votes still need migration and complete policy enforcement.
