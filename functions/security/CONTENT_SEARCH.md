# Authorized content-search pages

Local implementation, not deployed. Tests and runtime validation remain deferred at user request.

readContentSearchPage replaces both client Firestore search queries. Page 0 scans up to 60 keyword candidates; pages 1-5 scan up to 80 recent posts each. Ranking, matching, hidden-post filtering and the 20-comment display limit remain in the client, but candidate content crosses the callable boundary only after server authorization. The existing bounded search is not exhaustive. Offset pagination may skip/repeat during concurrent publication; the client deduplicates IDs.

The callable reuses verified bearer, auth revocation, account status and authoritative follower/block checks from readPublicProfile. It filters removed/uploading/failed and auto-hidden content, checks parent-post access before embedded comments, filters unavailable/blocked comment authors, and follows original post references for reposts (cycle/depth limits). Comment quotes use the current authorized comment, not the saved quote text. A private commenter on an accessible post remains visible if unblocked. Missing IDs and missing originals fail closed. Auth/Firestore checks are snapshots, not an atomic transaction across all returned content; access changes during or after the request remain a race to account for in further hardening.

Returned fields are explicitly projected; unknown post/comment/poll fields are excluded. Vote arrays contain only the caller's own vote state. Dates use ISO strings supported by the shared post/comment parser. Limits: 60 pages/minute per UID, 6 MiB response content, eight repost levels, 30 reply levels. Large/slow requests fail visibly. Per-author checks are cached within one page and can add latency; batch authorization is a future optimization.

Deployment: deploy readContentSearchPage and its existing readPublicProfile dependency before this client. Keep contentSearchLimits server-only. The local root Firestore rules are partial and lack the app's community_posts policy. This change removes direct reads from the search request path only; it does NOT secure every direct read elsewhere in the app or supersede live rules. Search card actions/live streams, original-post navigation and comment screens still require their own migration. Do not deploy the partial root rules over the complete live policy. A complete read-policy audit remains required before claiming end-to-end content confidentiality.
