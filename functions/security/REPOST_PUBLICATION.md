# Repost publication

Local implementation; automated/device tests deferred by the user.

publishRepost accepts exactly postId, sourcePostId, nullable commentId, title and body. Source snapshots, author identity, moderation, counters and media cannot be supplied. All three identified client publication helpers use it. It reuses authorized source preflight, verifies the bearer token, and transactionally checks cutoff, actor availability, destination/deletion receipt, source chain (maximum eight), source author availability, both block directions and authoritative followers. whoCanRepost supports everyone/followers/mutual/none, with an owner override. Post authors must also allow content access. A comment repost additionally checks the selected comment author's repost audience and all nested/legacy flat ancestors for availability and blocks. Unknown audience values fail closed.

The created quote stores only source IDs, source owner ID and optional comment kind/ID. Current source text and media come from the authorized quote reader; new reposts no longer store a persistent content snapshot. Repost notifications are created in the same transaction, skip self, use server identity and a deterministic destination-post key. A server-only receipt acknowledges an identical request without rewriting content, counters or notifications. Manual retries use a new client ID and can duplicate a repost after a lost response; refresh before retrying. Existing snapshot-based reposts are not backfilled.

Client permission hints now use readPublicProfile and fail closed on failure. Mutual hint uses the caller's own server-managed follower collection. The server remains authoritative at publication. Preview root lookup uses readAuthorizedPost instead of a raw collection query; existing fallback behavior and legacy flattening to a root post remain. Some legacy consumers that expect copied preview text can show less detail for reference-only quotes; the main quote card uses the authorized reader. Other readers and saved snapshots still need inventory before release.

Auth account-disabled checks occur in preflight; database privacy/block/source checks repeat transactionally. A changed Firebase Auth account status cannot be made atomic with Firestore. Privacy changes after publication are enforced on authorized reads, not by deleting references. Legacy raw readers, media URLs, storage policy and incomplete root rules remain outstanding; no full confidentiality claim. Do not deploy partial root rules. Deploy callables/profile projection before the client.
